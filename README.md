# 银行 AI 智能体

用户说人话，Agent 自主理解意图、规划任务链路，并在确定性安全框架内完成银行业务操作。
每一步可解释、可审计、可拦截。

> 这是一个比赛演示项目：银行核心是内存模拟实现，登录使用演示口令，制度语料是随包的 JSON。
> 它不连接真实银行系统，也不处理真实资金。替换真实核心时 Agent 侧逻辑一行不改。

## 快速开始

**环境要求**：Node.js ≥ 24、npm（不要用 pnpm，其符号链接在受限 Windows 环境会失败）

```powershell
npm install

# 可选：配置大模型。不配也能完整运行，会自动走离线确定性解析
copy .env.example .env
# 编辑 .env，填入 DEEPSEEK_API_KEY（申请地址：https://platform.deepseek.com/）
```

### 启动方式

| 方式 | 命令 | 说明 |
|---|---|---|
| 交互终端 | `npm run chat` | 自己打字和 Agent 对话（最贴近真实场景） |
| Web 界面 | `npm run dev` | 启动网关，浏览器打开 http://127.0.0.1:8787/ |

没有 API Key 时会自动回退到内置的确定性解析器，整条链路
（意图 → 计划 → 裁决 → 确认 → 执行 → 审计）依然完整跑通。

### 终端交互示例

```powershell
npm run chat

你 > 给老妈转800，备注买年货
你 > 我还有多少钱
你 > 查一下最近的异常交易
你 > 我的哪些卡有可用额度
```

需要回应的提示：

| Agent 说 | 你怎么回 |
|---|---|
| 「请确认以上信息」 | `确认` 执行 / `取消` 放弃 |
| 「需要你签署《风险不匹配确认书》」 | `签确认书`（`确认` 不能替代它） |
| 「有 2 位收款人都叫……」 | `1`、`第一个`，或说特征（`张伟设计`、`尾号1222`） |
| 「如何完成验证」 | `验证`（等价于真实环境的人脸识别） |
| 不想继续了 | `取消` 放弃，或 `转人工` |

## 部署 / 集成

### Web 网关接口

启动 `npm run dev` 后：

```powershell
# 健康检查（公开）
curl http://127.0.0.1:8787/api/health

# 登录（演示口令默认 demo-pass，可用 AUTH_DEMO_PASSWORD 覆盖）
curl -c cookies.txt -X POST http://127.0.0.1:8787/api/auth/login `
  -H "Content-Type: application/json" `
  -d '{"customerId":"CUST-DEMO-001","password":"demo-pass"}'

# 发消息
curl -b cookies.txt -X POST http://127.0.0.1:8787/api/channels/app/messages `
  -H "Content-Type: application/json" `
  -d '{"text":"给老妈转500","sessionId":"s1"}'

# 确认 / 取消
curl -b cookies.txt -X POST http://127.0.0.1:8787/api/channels/app/actions `
  -H "Content-Type: application/json" `
  -d '{"action":{"kind":"confirm"},"sessionId":"s1"}'
```

主要接口：

| 接口 | 作用 |
|---|---|
| `GET /api/health` | 健康检查 |
| `POST /api/auth/login` / `logout` | 登录 / 登出（服务端撤销） |
| `GET /api/auth/whoami` | 当前身份（来自服务端令牌） |
| `POST /api/channels/:channel/messages` | 发送消息（`app` / `im` / `web` / `voice`） |
| `POST /api/channels/:channel/actions` | 确认、取消等结构化动作 |
| `GET /api/audit/recent` / `verify` | 审计事件 / 链完整性校验 |
| `GET /api/sessions` | 历史会话列表 |

### 身份安全

- `customerId` 只从服务端签发的会话令牌里取；请求体里的 `customerId` 只作核对，不一致即 403 并留痕
- API Key 只存在于服务端进程内存，不进入浏览器、模型上下文或审计日志
- 模型输入先脱敏：卡号、证件号、手机号在进入模型前已替换
- `.env` 已在 `.gitignore` 中，不会被提交

### 替换真实银行核心

`packages/core` 只依赖一个 `BankCore` 接口（在 `types.ts` 里定义）。
把 `packages/bankcore` 换成接真实核心的实现，Agent 侧逻辑零改动。

## 项目结构

```
bank-agent/
├─ packages/
│  ├─ core/          # 领域核心(不依赖具体模型或数据库)
│  │  ├─ agent/      # 编排器、规划、受限专家、审计派生
│  │  ├─ capabilities/  # 能力注册表 + 各业务场景实现
│  │  ├─ policy/     # 策略引擎、评分器、提交点判据
│  │  ├─ intent/     # 意图契约、收款人消歧
│  │  ├─ security/   # 反诈干预、注入防御
│  │  ├─ retrieval/  # RAG(BM25、条款切分、拒答判定)
│  │  └─ audit/      # 审计哈希链
│  ├─ llm/           # 模型层(可替换,支持离线降级)
│  ├─ bankcore/      # 模拟银行核心 + 制度语料
│  ├─ server/        # 渠道网关 + Web 前端
│  └─ cli/           # 交互终端入口(chat.ts)
├─ tests/redteam.test.ts  # 安全回归测试
└─ tools/                # 端到端验证脚本
```

依赖方向始终向内：`core` 不知道 `llm` 的存在，`llm` 不知道 `bankcore` 的存在。
所以模型可以替换、银行核心可以替换，而核心安全逻辑一行不改。

## 六个业务场景

| 场景 | 能力 |
|---|---|
| **智能转账** | 按人名 / 手机号 / 备注转账；同名消歧；定时与周期转账；AA 收款；撤销；反诈干预；权限分级与强验证 |
| **账单分析** | 月度 / 年度报告；异常交易识别；定期支出识别；收支现金流；剩余预算规划 |
| **理财操作** | 产品列表与推荐；风险测评（C1–C5）；申购与赎回；风险不匹配须签确认书 |
| **卡片管理** | 列表与状态；提额资格与申请；解除限制；挂失冻结；补卡 |
| **订阅代扣** | 识别与续费提醒；一键取消；商户侧自动续费如实告知 |
| **跨场景事件联动** | 纪念日 / 发薪日 / 大额支出预备；四类数据汇总成方案；逐步确认 |

**通用能力**：制度问答（RAG，答不上来就拒答）、客户记忆（严格客户隔离）、材料比对（逐字段对照）、办事台（汇总已有事实）。

## 关键设计原则

1. **模型不做裁决** —— 大模型只把自然语言翻译成结构化意图 JSON。是否放行、需要哪种验证，由纯确定性策略引擎决定。
2. **注入防御是架构性的** —— 模型不裁决、不持有凭证、只能输出 JSON，所以"绕过权限控制"在架构上做不到。
3. **办不到的事，不说漂亮话** —— 回复发出前有出口闸门，扫描「已帮你取消」「保本保收益」这类话，命中就当场改写。
4. **取消只在提交点之前** —— 资金操作切成 `prepare`（零副作用）→ `commit`（唯一副作用点）→ `abort`（已提交则走补偿链）。没有"钱扣了、状态未知"这第四种。
5. **审计哈希链** —— 每条事件的哈希串上一条的哈希，任何一条被修改、删除或插入，后续校验全部失败并精确定位断点。
6. **前端不含业务判断** —— 页面只负责收发消息和渲染卡片，哪句话该被拦、要不要人脸、能不能挂失，全部由服务端决定。

## 已知边界（如实说明）

- 银行核心是内存模拟：余额、流水、卡片、理财产品均为演示数据
- 登录是演示口令：`verifyCredential()` 只证明"你知道演示口令"，生产必须替换为行方真实凭证核验
- 随包的评分模型是占位模型：合成标签只证明管道通了，不证明能识别欺诈
- 没有真实欺诈标签：反诈与风险评分依赖规则与话术特征，不是真实案件数据训练的模型
- 制度语料规模有限：RAG 仅覆盖随包约 20 条条款，超出范围会拒答而不是猜测
