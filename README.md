# 银行 AI 智能体 —— 智能转账 + 账单分析 + 理财操作 + 卡片管理 + 订阅代扣 + 跨场景事件联动

> 用户用自然语言描述需求,Agent 自主理解意图、规划任务链路,并在严格的安全框架内
> 完成银行业务操作。已实现**六个业务场景**:
> **场景一 · 智能转账**(权限分级 + 强验证 + 反诈)、
> **场景二 · 账单分析**(消费分类 / 异常识别 / 月度年度报告 / 定期支出 / 收支 / 洞察 / **预算规划**)、
> **场景三 · 理财操作**(产品对比 / 风险测评 / 申购赎回 / 持仓收益,含适配性合规规则)、
> **场景四 · 卡片管理**(挂失冻结 / 补卡 / 额度 / 限制诊断,含"申请 ≠ 已生效")、
> **场景五 · 订阅代扣管理**(自动识别 / 续费提醒 / 一键取消,含"本行关不了就如实说")与
> **场景六 · 跨场景事件联动**(通用事件触发:纪念日 / 生日 / 发薪日 / 大额支出预备 / 出行;
> 把账单、资金、订阅、外部商户汇总成一份**方案**,再把方案拆成"资金操作"与"外部服务操作"
> 两类步骤**逐步确认** —— 方案只出计划,一步都不执行),
> 六者共用同一套核心技术与安全架构。
>
> ★ **编号只给"一类业务"**:材料比对、异常复核(账单分析之上的深挖)、
> 检索增强(RAG)与跨会话客户记忆(通用能力)**都不占场景编号** ——
> 拿编号当"第几次迭代"的计数器,路标就会失效。
>
> 在此之上还有一层**交互体验扩展**(见 [文档 29](docs/29-交互体验扩展-流程可视化与个性化.md)):
> 办理流程可视化(每步标注"归谁办")、金额与规则的来源标注、个性化主动建议、
> 以及**可以真的记住并复用的常用流程**。

### 几种回应方式(遇到时照着做就行)

| Agent 说 | 你怎么回 |
|---|---|
| 「请确认以上信息」 | `确认` 执行 / `取消` 放弃(转账、理财申购与赎回都适用) |
| 「需要你签署《风险不匹配确认书》」 | **`签确认书`** ← 买超出自己风险等级的产品时必须先签;`确认` 不能替代它 |
| 「有 2 位收款人都叫……」 | `1` 或 `第一个`,也可以说特征:`张伟设计`、`招行那个`、`尾号1222` |
| 「如何完成验证」(要求强验证) | **`验证`** ← 等价于真实环境弹出的人脸识别 |
| 你不想继续了 | `取消` 放弃,或 `转人工` 转接坐席 |

> **关于人脸识别怎么完成**:真实产品里这一步是手机银行的**系统级**生物识别弹窗,
> 生物特征比对在硬件安全区完成,应用只拿到"成功/失败"和一个签名回执。
> 在本演示的文字界面里,回复「验证」就是它的等价物 —— 系统会打印出完整过程,
> 包括回执签发、载荷哈希绑定、验签。想看得更细可以用 `:auth` 命令。
>
> 注意:**Agent 不实现验证逻辑,也接触不到生物特征数据**。它只负责转交回执,
> 所以即使 Agent 被攻破也无法伪造验证。

内置调试命令(便于答辩现场展示内部机制):

| 命令 | 作用 |
|---|---|
| `:trace` | 查看最近一轮的**完整决策链路**(逐条审计事件) |
| `:audit` | 查看全部审计事件(含哈希链接关系) |
| `:verify` | **现场校验审计链完整性** |
| `:policy` | 查看当前策略配置(各档位阈值、时间窗口) |
| `:limits` | 查看权限分级矩阵(绿/黄/红/黑) |
| `:auth` | 展示强验证的完整内部过程(回执签发与验签细节)并执行 |
| `:handoff` | 模拟用户请求人工协助 |
| `-- --im` 启动参数 | 以 IM 渠道身份进入,体验渠道降级行为 |

## 它做什么

**一句话**:用户说人话,Agent 把事办了,而且每一步都可解释、可审计、可拦截。

```
👤 给老妈转2000,备注这个月生活费

   收款人:王秀兰        转账金额:¥2,000.00
   收款银行:中国工商银行  手续费:免手续费
   收款账号:**** 4455    付款账户:**** 9695
   备注:这个月生活费
   可撤销:发起后 5 分钟内、对方尚未入账前可撤销
   请确认以上信息。
```

🤖 风险等级不匹配:您的风险等级是 C3(平衡型),而「科技成长精选」是 R5(高风险),超出您的承受能力 2 档。
   按规定,购买超出自身风险等级的产品,需要您本人签署《风险不匹配确认书》后才能继续。

   产品:科技成长精选(LC3002)· R5 高风险
   金额:20,000 元
   您的等级:C3(平衡型),可购上限 R3

   《风险不匹配确认书》

   本人已充分了解:
     1. 本产品的风险等级高于本人风险承受能力等级;
     2. 该产品不保本、不保证收益,历史业绩不代表未来表现;
     3. 本人可能在短期内承受超出预期的本金损失;
     4. 本次签署系本人自主决定,未受任何他人误导或代操作。

## 七个核心主张

### 1. 模型永不做裁决

大模型在系统里**只有一个职责**:把自然语言翻译成结构化意图 JSON。
是否放行、需要什么级别的验证,由 `policy/engine.ts` 这个**纯确定性函数**决定。

为什么:审计员必须能逐条读完规则。LLM 的判断无法审计、无法复现、无法向监管解释。

```
风险分 = f(金额, 收款人新颖度, 画像偏离, 渠道风险, 设备可信, 时段, 名单, 拆分特征)
         − 信任降级
```

**因此"首次向新收款人转账"会被无条件升级为强验证,哪怕只转 50 元** ——
因为真实欺诈的最强预测因子是收款人的新颖度,不是金额。

### 2. 注入防御是架构性的,不是提示词性的

模型不裁决(I1)、不持有凭证(I2)、只能输出 JSON、不能拼字符串。
**所以"绕过权限控制"在架构上不可能** —— 不是"我们挡住了",是"它做不到"。

检测到越权指令时,系统**不会拒绝用户**(因为它无法提权,拒绝只会误伤),
只记录审计、提高验证强度、如实告知。

### 3. 反诈干预:对话式 Agent 独有的机会

名单库只能覆盖已知账户。而**受害者的话里有信号** ——
"不要告诉银行的人""马上要截止了""他教我操作"。

传统 App 的转账页面拿不到这些;对话式 Agent 拿得到。

干预方式不是"再弹一个窗"(受害者会直接点确定),而是:
**冷静期 + 点名话术套路 + 引导客户自己发现矛盾**。

设计立场:**不替客户做决定,而是确保他在不被话术控制的状态下做决定。**
直接拒绝会把客户推向其他渠道甚至线下,反而彻底失去干预机会。

### 4. 理财场景:把监管规则写成代码,而不是写成提示词

理财场景有三条绕不过去的合规要求:**首次购买理财必先风险测评**、
**不得把超出客户风险等级的产品卖给他**、**不得承诺保本保收益**。
这三条在本项目里**全部实现为确定性硬规则** —— 写在策略引擎与响应出口里,
**命中即生效,没有例外路径,也没有"管理员可以跳过"的后门**。

为什么:监管要看的是"你有没有能力不违规",而不是"你有没有在提示词里叮嘱模型别违规"。
提示词是**请求**,代码是**保证**;只有后者可以在事后逐条复现给审计与监管看。

**权限分级矩阵(理财部分)**:

| 规则 ID | 触发条件 | 后果 |
|---|---|---|
| `R-WEALTH-ASSESSMENT-REQUIRED` | 客户未完成风险测评,或测评已过期(一年一评) | **阻断申购**,并引导去做测评。★ 拦的是**申购动作**,不拦产品浏览 —— 用户可以自由看、自由比,只是不能买 |
| `R-WEALTH-RISK-MISMATCH` | 产品风险等级 > 客户风险承受等级 | **阻断**,须签署《风险不匹配确认书》;已签且有效则放行,放行与拒绝**都留痕** |
| `enforceWealthWording`(输出侧合规闸门) | 响应文本出现「保本保收益」「稳赚不赔」等违规承诺 | **整句删改** + **如实告知用户哪句话被改过**(不静默改写) |

一个具体的坑,说明为什么"必须是代码":
如果把"不要承诺保本保收益"只写进提示词,那么当客户问
**「有没有保本又能有 5% 收益的?」**时,模型很可能**复述客户的原话**来回答 ——
违规措辞就这么发出去了,而提示词里没有任何机制能在**发出去之前**拦住它。
实现为出口闸门之后就不一样了:**即使模型被说服,它也没有办法把违规的话说出去**。
这与注入防御是同一个道理 —— **安全不能靠模型自律**。

另外,确认书**绑定「客户 + 产品 + 金额」**三者,任一项变化即失效 ——
想靠改金额把确认书挪用到另一笔上,做不到。

### 5. ★ 办不到的事,一句漂亮话也不说

这一类错误在银行业 Agent 里最不显眼,却最伤客户:

| 场景 | 模型的"漂亮话" | 真实后果 |
|---|---|---|
| 商户侧自动续费(iCloud 等) | 「已帮你取消」 | 下个月照扣,而客户已经不知道该找谁 |
| 取消订阅 | 「费用会原路退回」 | 取消 ≠ 退款,客户以为钱会回来 |
| 卡片限制 | 「已经帮你解除了」 | 实际只是提交了申请,银行还没批 |
| 跨场景事件联动 | 「已经帮你安排好了」 | 客户以为礼物订好了、钱也留出来了,直到当天才发现**一步都没执行** |
| 理财 | 「保本保收益」 | 违规承诺 |

系统对这类话有**四道出口闸门**(`enforceWealthWording` / `enforceCardWording` /
`enforceSubscriptionWording` / `enforceEventPlanWording`):回复在发出之前逐句扫描,命中就**当场改写**,
并**如实告诉客户哪一句话被改过** —— 静默改写同样是欺骗。
第四道闸门还多一层:只办了资金那一步时,不许说成"外部也提交了";
提交了外部订单时,不许说成"订单已完成/已送达"。

与之配套的是**能力分级本身的诚实性**:「本行没有这份代扣协议」不是一个失败,
而是一个正确答案。系统区分三件事:

> **我看见了**(流水里有这笔扣款)—— **我能处理**(本行有可解的协议)—— **我办成了**(协议状态已改)。

把这三件事混成一件,Agent 就会变成"什么都说好"的客服。
本项目的立场是:**宁可说办不到,不可说办成了。**

### 6. 身份与频次:同样是裁决,不是中间件

前五项都在讲"钱怎么动";这一项讲"谁在动、动得多快"。

**身份**:`customerId` **只从服务端签发的会话令牌里取**,请求体/查询串里出现的
`customerId` 降级为**核对项** —— 不一致就 403,并把"他声称是谁"与"令牌里是谁"
一起写进哈希链。所以横向越权(拿别人的客户号调接口)不是"被中间件挡住",
而是**在系统里没有一条路径能把那个客户号变成身份**。

**频次**:限流**没有**做成 `if (count > N) return 429`,而是策略引擎里的一类硬规则 ——
`R-FREQUENCY-LIMIT` / `R-INJECTION-COOLDOWN`,产出与名单命中、拆分检测**同构**的
`PolicyReason`(带规则 ID、窗口、计数、上限),照旧进审计链。
转账 5 分钟 ≤3 次、凭证变更 30 分钟 ≤3 次、只读 1 分钟 ≤60 次;
连续 3 次命中注入检测 → 会话进入冷却(偶发一次不冷却)。

为什么:限流如果写在 HTTP 层,它**进不了审计链**,也解释不了"为什么是这一笔被拦" ——
对客户说不出理由、对审计拿不出证据的拦截,等于没有裁决。

### 7. ★ 取消与升级:同样先定义"点",再谈动作

这一项讲两件看起来不相关、其实是同一件事的事:**什么时候可以中止**、**谁来算那个分**。
两件都坚持同一个做法 —— 先在制度里定义清楚那个"点",再谈动作。

**提交点(节点内中断)**:资金操作的"取消"只有在**提交点之前**才可能是干净的。
提交点不由执行器猜,而是定义在银行核心的接口上:`prepareOperation`(零副作用) →
`commitOperation`(**唯一的副作用点**) → `abortOperation`(已提交则如实回报 `alreadyCommitted`)。
所以"取消"是一份**只读的意图数据**,在提交边界被读一次,而不是一个能随时杀死执行的信号。

于是结局**恰好三种**,没有"钱扣了、状态未知"这第四种:

| 结局 | 审计证据 | 钱 |
|---|---|---|
| 未提交·余额不变 | `execution_cancelled`(写明 `before_commit`、未扣款) | 一个字节没动 |
| 已提交·走补偿 | `compensation_started` / `compensation_completed`(逆序) | 已动,靠补偿收回 |
| 业务失败 | `execution_failed` | 未动 |

提交点之后客户说"取消",系统**不会假装把钱退回来** —— 它走的是既有的补偿链;
没有登记补偿动作的节点如实标记"需人工处理"。四个真正动钱的操作有提交点,
撤销/补偿类动作**故意没有**提交点(在补救路径上允许取消,等于拒绝把损失还回去)。

**取消意图有三个入口,后果只允许一种**:客户说"取消整批"(文本)、界面上的「取消」按钮
(结构化动作)、上游/网关带进来的 `cancel` 字段。三条都汇到同一条路径,
审计用 `request_rejected.payload.trigger` 区分来源。★ 两条口径上的"两张皮"就是这样被抓出来的:
① 按钮入口原来**只删待办**并回一句"没有执行任何操作",而多步计划的第一步**可能已经提交** ——
用嘴说会补偿、用手点却把钱留在世界上;② HTTP 入口的取消意图一度用对象展开塞进信封,
而**对象展开不触发 TypeScript 的多余属性检查** —— 编译器因此一声不响、字段在运行期被悄悄丢掉,
客户按了取消钱照转。两条都已修并有断言钉住
(`★ 提交点` 组的「点按钮取消 == 说「取消」」与 `verify-gateway` 第 7 段)。

**评分器可替换**:评分(算 0–100 分)与分级(`mapScoreToTier`)本来就是分开的,
所以"换评分器"不需要动裁决体系。三种模式,**默认最保守的那个**:

| 模式 | 谁在裁决 | 用途 |
|---|---|---|
| `legacy`(**默认**) | 手调线性权重 | 升级前后既有行为一个字没变 |
| `shadow` | **仍是 legacy** | 并行算挑战者分并记录**分歧**,只报告不下场 |
| `logistic` | 训练出的逻辑回归 | 接管评分;阈值 28/62、硬规则、名单/拆分顶格全不动 |

切换的唯一入口是 `configureScorer(mode, model)` —— 升级是**显式动作**,不会因为
"代码里更新了模型文件"就悄悄改变线上行为。可解释性契约也保住了,而且成了**可核对恒等式**:
`基准分(model_base) + Σ 各因子贡献 = 模型分`,sigmoid 的非线性残差被显式写进基准分的说明里。

★ **诚实边界(这一项最要紧的一句话)**:比赛环境**没有真实欺诈标签**。
合成的标签只证明"记录 → 特征 → 标签 → 训练 → 影子对比"这条管道是通的,
**证明不了模型能识别欺诈**;当前随包的模型是**未训练的占位模型**,
文件里如实写着 `labelSource: "synthetic_demo"`。要判断效果,必须用真实结局
(`npm run label-outcomes -- --feed=…`)并做时间切分的留出集评估。

| **`npm run scorer-report`** | **★ 新旧评分器对比报告**(第 4 项第 4 步):同一批历史请求在 legacy 与挑战者下的档位分布 + 分歧清单 + `scorer_divergence` 事件计数 + 模型的 `id/labelSource/sampleSize/note`;`--model=<path>` 对比**任意候选模型文件**(不必先覆盖基线),`--json` 供脚本消费 |
| `npm run check-llm` | 模型连通性排查(Key、网络、返回格式) |
| `npm run redteam` | 与 `npm test` 同义(红队安全回归) |

### 交互体验的四个扩展(在 Agent 大脑之上加的一层)

> 设计说明见 [29 交互体验扩展](docs/29-交互体验扩展-流程可视化与个性化.md)。

| 扩展 | 客户看到什么 | 它凭什么可信 |
|---|---|---|
| **办理流程可视化** | 每条回复下面一条步骤链路,每一步标着**归谁办**:Agent 自主执行 / 等您确认 / 需您本人验证 / **已转人工审批** / 已被拦截 | 流程是**从本轮审计事件翻译出来的**,不是画出来的 —— 界面说"已办结"⇔审计里必有 `execution_completed` |
| **来源标注** | 涉及金额或规则时给出「来源 · 主体 · 时效 · 计算过程」,如 `剩余 = 5,000.00 − 16,207.92 = −11,207.92` | 数字在**产生它的能力里**登记出处,统一渲染;规则出处来自策略裁决本身 |
| **个性化建议** | 「本月你已支出 ¥16,207(44 笔)。要帮你规划这个月剩余预算吗?」——点一下就能办 | 规则是纯函数、依据必须写出来(`reason` 字段进审计);同一条建议 6 小时内不重复推 |
| **人工审批** | 敏感流程明确提示~~「已转人工审批」~~ **「已转人工审批 + 请提交以下材料 + 从哪交 + 多久出结果」** | 材料清单来自规则库,由出口**强制插入**:只要审计里有审批节点,就一定会告诉客户交什么 |
| **材料比对** | 三份材料并排对照,矛盾行整行标红、差异值加 `≠`,顶部一句"发现 4 处矛盾,其中 3 处实质性" | 比对是纯函数:金额按数值+容差、文本按二元组重合度;表述不同但同一事项**不误报** |
| **异常复核** | 问"还有没有漏"时,先给两条评分(重扫成本 / 遗漏风险)再决定扫不扫 | 两项评分由已知事实推出并**双双进审计**,事后能回答"为什么不重扫" |
| **误报撤回** | 证据 → 撤回哪条(保留原判定依据)→ 还剩哪条要复核 | 撤回不是删除:依据与客户原话全部留痕,重扫也不会让误报复活 |

### 检索增强:制度问答 + 客户记忆(RAG 阶段 1+2)

> 设计说明见 [31 会话管理与检索增强](docs/31-会话管理与检索增强-实施方案.md)、[32 RAG 实施方案](docs/32-RAG实施方案.md)。

| 能力 | 客户问什么 | 它怎么答 |
|---|---|---|
| **制度问答** `policy.search` | 「白金卡年费多少」「补卡多少钱」「转错了能撤销吗,多长时间内」 | 命中**条款原文**并原样引用,同时给出**文档版本 + 生效日期 + 出据方 + 置信度**;答不上来就**拒答**并建议转人工 |
| **客户记忆** `memory.search` | 「刚才那笔转账成功了吗」「我上个月那笔为什么失败」「我们上次聊了什么」 | 从**操作台账 / 会话记录 / 记账批注 / 提交材料**里检索,答出**时间 + 记录原文 + 流水号**;说「刚才」时以时间排序 |

三条刻意的边界:

1. **检索只给依据,不给数字**。制度里没有客户的余额 —— 金额/余额/额度类问题**根本不进检索**,
   一律交给结构化能力;`verify-rag` 会逐条回查"回答里的每个数字都能在条款原文里找到"(越界 = 0)。
2. **宁可不答,不可猜答**。三条硬条件(分数、覆盖率、与第二名差距)同时满足才作答;
   不满足就回固定拒答话术。客户会照着条款去办事,猜错的代价由客户承担。
3. **客户记忆严格按客户隔离**。`customerId` 只从执行上下文取,入参不接受客户 ID;
   「另一个客户问同一句话」在索引层与对话层都必须零命中(硬断言)。

### ★ 单 Agent 还是多 Agent?

**单控制面单 Agent** —— 一个编排器 + 一份确定性策略引擎。这是刻意的:裁决不能外包,
权限不能在子 Agent 之间扩散,结论必须能逐条复现给审计看。

多 Agent 的价值用**受限专家**的形态保留:材料比对交给 `doc_analyst`、异常复核交给 `review_officer`,
两者都**只读**、只有**白名单**能力,每次派发都进审计(`specialist_dispatched`)。
一句话:**用多 Agent 的结构收窄权限,不用它的自治性放松裁决**。详见 [文档 30](docs/30-第二轮打磨-流程更新与复核决策.md)。

**★ 常用流程存在哪里**:客户**明确要求**时(点流程卡上的「存为常用流程」,或说「把刚才那个存成常用流程」),
系统把它记成一条**意图模板**(如 `给 王秀兰 转 {金额,如500.00} 元,备注 {备注,如买菜}` —— 金额是参数,不是冻死的数字),
放在 **App 首页 → 常用服务 → 我的常用流程**,点一下就填进输入框。
落盘在 `var/personalization/<客户ID>.json`(原子写入),**换进程、换浏览器都还在**。
也可以直接在对话里说「用一下给老妈转账」。

> 两条刻意的边界:
> ① **系统不会自动往里塞** —— "常用"的定义权属于客户,首页只展示客户真的用过的一两条;
> ② **常用流程省的是打字,不是确认** —— 点名调用只会被补全成完整请求,
> 然后照常走策略裁决与确认卡,绝不跳过任何一步。

## 渠道网关 API

> ★ **身份只来自服务端签发的令牌,不来自请求体。**
> 会话令牌放在 HttpOnly Cookie(`ba_session`)里,浏览器自动携带;
> 请求体/查询串里如果出现 `customerId`,它**只作核对** —— 与令牌身份不一致即 403
> 并写入哈希链(`auth_denied` / `cross_customer`)。
> 下面用 `curl -c/-b` 手动带 Cookie 罐,等价于浏览器行为。

```powershell
# 健康检查(公开,不需要身份)
curl http://127.0.0.1:8787/api/health

# 登录(演示口令默认 demo-pass;可用 AUTH_DEMO_PASSWORD 覆盖)
#   → 成功时返回 Set-Cookie: ba_session=...(HttpOnly; SameSite=Strict)
curl -c cookies.txt -X POST http://127.0.0.1:8787/api/auth/login `
  -H "Content-Type: application/json" `
  -d '{"customerId":"CUST-DEMO-001","password":"demo-pass"}'

# 我是谁(身份来自令牌,返回 customerIdSource: session_token)
curl -b cookies.txt http://127.0.0.1:8787/api/auth/whoami

# 通过 APP 渠道发消息
curl -b cookies.txt -X POST http://127.0.0.1:8787/api/channels/app/messages `
  -H "Content-Type: application/json" `
  -d '{"text":"给老妈转500","sessionId":"s1"}'

# 确认操作
curl -b cookies.txt -X POST http://127.0.0.1:8787/api/channels/app/actions `
  -H "Content-Type: application/json" `
  -d '{"action":{"kind":"confirm"},"sessionId":"s1"}'

# 查看审计事件(按身份过滤:只返回自己的事件)
curl -b cookies.txt http://127.0.0.1:8787/api/audit/recent

# 校验审计链完整性(全局结论,不含事件内容)
curl http://127.0.0.1:8787/api/audit/verify

# 常用流程与个性化(首页"常用服务"的数据来源)
curl -b cookies.txt http://127.0.0.1:8787/api/personalization

# 把某条常用流程实例化成一句可发送的话
curl -b cookies.txt -X POST http://127.0.0.1:8787/api/flows/instantiate `
  -H "Content-Type: application/json" `
  -d '{"templateId":"flow_xxx","values":{"amount":"888"}}'

# 保存常用流程(只传 traceId + sessionId,模板由服务端重新派生)
curl -b cookies.txt -X POST http://127.0.0.1:8787/api/flows/save `
  -H "Content-Type: application/json" `
  -d '{"traceId":"trace_xxx","sessionId":"s1"}'
```

渠道:`app` | `im` | `web` | `voice`。
**同一套消息信封,同一个 Agent 核心** —— 渠道差异只体现在一张能力表里。

### 安全边界(与本项目其它部分同一立场)

| 机制 | 行为 |
|---|---|
| 身份 | 签名令牌(HMAC-SHA256)`b1.<payload>.<sig>`;篡改一个字符即失效;登出由**服务端**撤销 |
| 越权 | 请求体/查询串里的 `customerId` 与令牌不一致 → 403 + `auth_denied(cross_customer)`(审计同时记录"声称是谁/其实是**谁**") |
| CORS | 白名单:实际绑定的 `127.0.0.1:<port>` / `localhost:<port>` + `ALLOWED_ORIGINS`;**没有 `*`**,白名单外来源 403 并留证 |
| CSRF | `SameSite=Strict` + Origin 白名单 + 拒绝 `Sec-Fetch-Site: cross-site` + 可选 `X-CSRF-Token` 双提交 |
| 回执签发 | `/api/demo/sign-auth-proof` 的签名对象**只由服务端认定**(refId → 载荷哈希 → 本会话最新待办),并校验归属;不是"给什么签什么" |
| 登录节流 | 5 次失败 → 5 分钟冷静期(冷静期内连正确口令也拒),429 之前**先写审计** |
| 限流 | 策略引擎硬规则(转账 5 分钟 ≤3 次、凭证变更 30 分钟 ≤3 次…),超限产出 `R-FREQUENCY-LIMIT` 理由进哈希链 |
| 注入冷却 | 连续 3 次命中注入检测 → 会话冷却,期间操作被 `R-INJECTION-COOLDOWN` 拦下(偶发一次不冷却) |
| 严格模式 | `AUTH_REQUIRE_LOGIN=1`:关闭演示引导,未登录一律 401 并留证 |

> 演示默认(`AUTH_REQUIRE_LOGIN` 未设)下,不带 Cookie 的首次访问会被引导出一个
> **只能指向默认演示客户**的会话(`demo_bootstrap`,事件同样进哈希链)——
> 这是"前端一行不改也能跑通"的实现方式:身份仍然是**服务端指派**的。
> 另外:演示银行核心没有真实凭证概念,登录只证明"你知道演示口令",
> 生产环境必须把 `verifyCredential()` 换成行方真实凭证核验。

## 安全说明

1. **API Key 只存在于服务端进程内存**,永不进入浏览器、模型上下文或审计日志;
2. **模型输入先脱敏**:卡号、证件号、手机号在进入模型前已替换;
3. **模型输出后校验**:金额字段必须对应工具返回值,否则响应被拒绝(I3);
4. **审计日志记录模型版本与提示词哈希**,不记录 Key 与敏感字段;
5. `.env` 已在 `.gitignore` 中,不会被提交;
6. **理财合规规则是硬编码的确定性判据**:未测评拦截、风险不匹配须签确认书、禁止保本保收益话术,全部由策略引擎与输出侧闸门强制,不依赖模型自律;确认书绑定「客户+产品+金额」,任一项变化即失效;
7. **取消只在提交点之前有效**:提交点定义在银行核心接口上(`prepare → commit`),已提交的操作**不会假装中止** —— `abortOperation` 如实回报 `alreadyCommitted`,后续只能走补偿链;没有登记补偿动作的节点如实标记"需人工处理";
8. **评分器可替换,但默认不变、且从不单独裁决**:默认 `legacy`,切换必须显式调用 `configureScorer()`;阈值(28/62)、硬规则、名单/拆分硬命中顶格永不由模型决定;当前随包的模型是**未训练的占位模型**,合成标签只能证明管道通了、证明不了模型有效。
