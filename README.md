# 银行 AI 智能体

用户说人话，Agent 自主理解意图、规划任务链路，并在确定性安全框架内完成银行业务操作。
每一步可解释、可审计、可拦截。

已实现六个业务场景：**智能转账**、**账单分析**、**理财操作**、**卡片管理**、**订阅代扣**、
**跨场景事件联动**。另有四项通用能力：**制度问答（RAG）**、**客户记忆**、**材料比对**、
**办事台**。

> 这是一个参赛演示项目：银行核心是内存模拟实现，登录使用演示口令，制度语料是随包的 JSON。
> 它不连接真实银行系统，也不处理真实资金。

## 快速开始

**环境要求**：Node.js ≥ 24、npm（不要用 pnpm，其符号链接在受限 Windows 环境会失败）

```powershell
npm install

# 可选：配置大模型。不配也能完整演示，会自动走离线确定性解析
copy .env.example .env
# 编辑 .env，填入 DEEPSEEK_API_KEY（申请地址：https://platform.deepseek.com/）

npm run typecheck   # 类型检查
npm test            # 红队安全回归：396 个断言 / 77 组
npm run demo        # 端到端演示：54 个场景
npm run chat        # 交互模式：自己打字和 Agent 对话（答辩推荐）
npm run dev         # 启动网关，浏览器打开 http://127.0.0.1:8787/
```

没有 API Key 时会自动回退到内置的确定性解析器，整条链路
（意图 → 计划 → 裁决 → 确认 → 执行 → 审计）依然完整跑通，只是自然语言理解能力弱一些。

## 怎么演示

脚本演示只能证明固定的 54 句话能跑通，证明不了"现场理解"。答辩建议用交互模式：

```powershell
npm run chat
```

进去之后直接说人话：

```
你 > 我这个月餐饮花了多少?
你 > 给老妈转800,备注买年货
你 > 我有5万块,推荐几个理财产品
你 > 我下个月15号有个重要纪念日帮我规划下
```

遇到需要回应的提示时：

| Agent 说 | 你怎么回 |
|---|---|
| 「请确认以上信息」 | `确认` 执行 / `取消` 放弃 |
| 「需要你签署《风险不匹配确认书》」 | `签确认书`（`确认` 不能替代它） |
| 「有 2 位收款人都叫……」 | `1`、`第一个`，或说特征：`张伟设计`、`尾号1222` |
| 「如何完成验证」 | `验证`（等价于真实环境的人脸识别） |
| 不想继续了 | `取消` 放弃，或 `转人工` |

内置调试命令：

| 命令 | 作用 |
|---|---|
| `:trace` | 最近一轮的完整决策链路 |
| `:audit` | 全部审计事件（含哈希链接关系） |
| `:verify` | 现场校验审计链完整性 |
| `:policy` | 当前策略配置（各档位阈值、时间窗口） |
| `:limits` | 权限分级矩阵（绿/黄/红/黑） |
| `:auth` | 强验证的完整内部过程并执行 |
| `:handoff` | 模拟请求人工协助 |

## 六个场景能做什么

| 场景 | 能力 |
|---|---|
| **智能转账** | 按人名 / 手机号 / 备注 / 别名转账；同名消歧；定时与周期转账；拆分 AA；未清算窗口撤销；反诈干预；权限分级与强验证 |
| **账单分析** | 月度 / 年度报告；异常交易识别；定期支出识别；收支现金流；综合洞察；剩余预算规划（带算式）；财务健康标签 |
| **理财操作** | 产品列表与推荐；多维对比；风险测评（C1–C5）；申购与赎回；持仓收益；到期续接方案；风险不匹配确认书；输出侧合规闸门 |
| **卡片管理** | 列表与状态；提额资格与申请（申请 ≠ 已生效）；交易限制原因诊断；解除限制申请；挂失冻结；补卡；激活与交易密码规则；新卡申请；改手机号 / 改密码（一律不代理） |
| **订阅代扣** | 自动识别（关键词 + 固定周期金额两条路径）；续费提醒；一键取消；商户侧自动续费（关不了就如实说）；房租等规律性付款的明确排除 |
| **跨场景事件联动** | 通用事件触发器（纪念日 / 生日 / 发薪日 / 大额支出预备 / 出行）；四类数据汇总成方案；资金操作与外部服务操作分开逐步确认；每笔去向与金额先披露；方案 30 分钟有效 |

**通用能力**

| 能力 | 说明 |
|---|---|
| 制度问答 | 命中条款原文并原样引用，给出文档版本、生效日期、出据方与置信度；答不上来就拒答 |
| 客户记忆 | 从操作台账、会话记录、批注、提交材料里检索，严格按客户隔离 |
| 材料比对 | 多份合同 / 报价 / 发票逐字段对照，矛盾行高亮；纯函数，可复算 |
| 异常复核 | 先给"重扫成本 / 遗漏风险"两条评分，再决定扫不扫；不无脑重试 |
| 办事台 | App 左上角的「待您处理 / 为您留意」，只汇总已有事实，点下去只是继续对话 |

## 关键设计

### 1. 模型不做裁决

大模型在系统里只有一个职责：把自然语言翻译成结构化意图 JSON。
是否放行、需要哪种验证，由 `policy/engine.ts` 这个纯确定性函数决定。

所以"首次向新收款人转账"会被无条件升级为强验证，哪怕只转 50 元 ——
真实欺诈的最强预测因子是收款人新颖度，不是金额。

### 2. 注入防御是架构性的

模型不裁决、不持有凭证、只能输出 JSON。所以"绕过权限控制"在架构上做不到，
不是"被挡住了"。检测到越权指令时不拒绝用户（它无法提权，拒绝只会误伤），
只记录审计、提高验证强度、如实告知。

### 3. 办不到的事，不说漂亮话

系统对"已帮你取消""已经解除了""保本保收益"这类话有四道出口闸门，
回复发出前逐句扫描，命中就当场改写，并如实告诉客户哪一句被改过。
能力分级也是诚实的：「本行没有这份代扣协议」不是失败，是正确答案。

### 4. 身份与频次同样是裁决

`customerId` 只从服务端签发的会话令牌里取；请求体里的 `customerId` 只作核对，不一致就 403 并留痕。
限流不是 HTTP 层的 429，而是策略引擎里的硬规则（`R-FREQUENCY-LIMIT` / `R-INJECTION-COOLDOWN`），
理由照旧进审计链。

### 5. 取消只在提交点之前

资金操作的接口被切成 `prepareOperation`（零副作用）→ `commitOperation`（唯一副作用点）→
`abortOperation`（已提交则如实回报）。结束时只有三种结局：未提交（余额不变）、
已提交（走补偿链）、业务失败 —— 没有"钱扣了、状态未知"这第四种。

### 6. 审计哈希链

每条事件的哈希串上一条的哈希，任何一条被修改、删除或插入，后续校验全部失败并能精确定位断点。
普通日志只能证明"我们记了"，哈希链能证明"我们没改过"。

### 7. 前端不含业务判断

手机银行页面只负责收发消息和渲染卡片，哪句话该被拦、要不要人脸、能不能挂失，
全部由服务端决定。前端里没有一行业务判断。

## 项目结构

```
bank-agent/
├─ packages/
│  ├─ core/                      # 领域核心(不依赖任何具体模型或数据库)
│  │  ├─ src/types.ts            # 全部契约与不变量
│  │  ├─ src/agent/              # 编排器、任务规划、受限专家、流程派生、来源标注、建议、审批
│  │  ├─ src/capabilities/       # 能力注册表 + 转账手续费 / 理财 / 卡片 / 账单 / 订阅 / 事件联动 / 材料比对 / 检索
│  │  ├─ src/policy/             # 策略引擎、评分器、提交点判据、评分模型
│  │  ├─ src/intent/             # 意图契约、收款人消歧、姓名模糊匹配
│  │  ├─ src/security/           # 反诈干预、注入防御
│  │  ├─ src/retrieval/          # BM25、分词、按条款切分、拒答判定
│  │  └─ src/audit/hashChain.ts  # 审计哈希链
│  ├─ llm/                       # 模型层(可替换,支持离线降级)
│  ├─ bankcore/                  # 模拟银行核心 + 制度语料
│  ├─ server/                    # 组装根、渠道网关、会话记录、个性化存储、App 前端
│  └─ cli/                       # demo / chat / probe / 评分器工具
├─ tests/redteam.test.ts         # 396 个安全断言,77 组
├─ tools/                        # 端到端验证与静态检查脚本
├─ var/                          # 运行时数据(审计链 / 会话 / 常用流程),不入库
└─ docs/                         # 设计文档,不入库
```

依赖方向始终向内：`core` 不知道 `llm` 的存在，`llm` 不知道 `bankcore` 的存在。
所以模型可以替换、银行核心可以替换，而核心安全逻辑一行不改。

## 移动端 App 与网关

启动网关后打开 `http://127.0.0.1:8787/`，是一个手机银行 App 的聊天界面：

- **首页**：问候语 + 八个快捷入口 + 卡片横滑概览；
- **左上「办事台」**：待您处理 / 为您留意，只汇总已有事实；点下去只是继续对话，不是「确认」；
- **对话**：确认卡渲染成结构化卡片（字段逐行、警告高亮、可撤销说明）；同一会话可连续办多件事，刷新后这一段还在；
- **待办按钮**：需要确认时出现「确认执行 / 取消」，需要强验证时出现「完成身份验证」；
- **盾牌按钮**：审计面板，显示哈希链完整性、事件总数与最近事件。

这个页面就是 `app` 渠道的真实前端：它发出的消息与 IM、语音渠道进来的一句话走同一段代码、
同一套策略引擎与审计链。

**身份只来自服务端签发的令牌**，放在 HttpOnly Cookie（`ba_session`）里。
请求体或查询串里的 `customerId` 只作核对，与令牌不一致即 403 并写入哈希链。

```powershell
# 健康检查(公开)
curl http://127.0.0.1:8787/api/health

# 登录(演示口令默认 demo-pass,可用 AUTH_DEMO_PASSWORD 覆盖)
curl -c cookies.txt -X POST http://127.0.0.1:8787/api/auth/login `
  -H "Content-Type: application/json" `
  -d '{"customerId":"CUST-DEMO-001","password":"demo-pass"}'

# 发消息
curl -b cookies.txt -X POST http://127.0.0.1:8787/api/channels/app/messages `
  -H "Content-Type: application/json" `
  -d '{"text":"给老妈转500","sessionId":"s1"}'

# 确认 / 取消
curl -b cookies.txt -X POST http://127.0.0.1:8787/api/channels/app/actions `
  -H "Content-Type: application/json" `
  -d '{"action":{"kind":"confirm"},"sessionId":"s1"}'
```

主要接口：

| 接口 | 作用 |
|---|---|
| `GET /api/health` | 健康检查（公开） |
| `POST /api/auth/login` / `logout` | 登录 / 登出（服务端撤销） |
| `GET /api/auth/whoami` | 当前身份（来自令牌） |
| `POST /api/channels/:channel/messages` | 发送消息（`app` / `im` / `web` / `voice`） |
| `POST /api/channels/:channel/actions` | 确认、取消等结构化动作 |
| `GET /api/audit/recent` / `verify` | 审计事件（按身份过滤）/ 链完整性 |
| `GET /api/sessions` | 历史会话列表 |
| `GET /api/ledger/recent` | 操作台账 |
| `GET /api/personalization` | 常用流程与个性化数据 |
| `POST /api/flows/instantiate` / `save` / `delete` | 常用流程实例化、保存、删除 |
| `GET /api/demo/pending` | 当前待办（办事台数据来源） |
| `POST /api/demo/sign-auth-proof` | 演示用强验证回执签发 |

## 安全说明

1. API Key 只存在于服务端进程内存，不进入浏览器、模型上下文或审计日志；
2. 模型输入先脱敏：卡号、证件号、手机号在进入模型前已替换；
3. 模型输出的金额必须对应工具返回值，否则响应被拒绝；
4. `.env` 已在 `.gitignore` 中，不会被提交；
5. 理财合规规则是硬编码的确定性判据：未测评拦截、风险不匹配须签确认书、禁止保本保收益话术；
6. 取消只在提交点之前有效，已提交的操作走补偿链，不假装中止；
7. 评分器可替换，但默认 `legacy`，切换必须显式调用 `configureScorer()`。

## 已知边界（如实说明）

- **银行核心是内存模拟**：余额、流水、卡片、理财产品均为演示数据，不连接真实核心；换成真实核心时 Agent 侧逻辑不需要改。
- **登录是演示口令**：`verifyCredential()` 只证明"你知道演示口令"，生产环境必须替换为行方真实凭证核验。
- **随包的评分模型未训练**：`policy/model/logisticV1.ts` 是占位模型，文件里写着 `labelSource: "synthetic_demo"`。合成标签只证明"记录 → 特征 → 标签 → 训练 → 影子对比"这条管道通了，**证明不了能识别欺诈**；要判断效果必须用真实结局做时间切分评估。
- **没有真实欺诈标签**：反诈与风险评分的效果在演示中依赖规则与话术特征，不是真实案件数据训练的模型。
- **制度语料规模有限**：RAG 仅覆盖随包的约 20 条条款，超出范围会拒答，而不是猜测。
- **审计链证明的是"未被修改"**：它能定位篡改断点，不等同于合规认证。
- **前端是演示界面**：`packages/server/public` 是可直接运行的 App 页面，不是发布到应用商店的安装包。
